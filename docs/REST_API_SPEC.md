## Read this first — an important framing note

The Architecture document (§3) established a deliberate decision:

> **There is no custom backend server.** Supabase provides three managed services — Auth (GoTrue), a REST API (PostgREST), and Postgres.

This means the "REST API" you consume is **auto-generated by PostgREST** for every table, plus **Supabase Auth** for login, plus **one custom RPC function** for reordering. You do not write a single HTTP handler. But you **do** need to know the exact request shapes, error codes, and conventions — because you'll write the `repository.js` layer against them and you'll debug them when something fails.

This document specifies that surface as a formal API contract. It is organized so that:

1. Every endpoint your frontend calls is documented with method, URL, body, response, and errors.
2. Every endpoint you *don't* need is explicitly excluded (§10), so nobody adds scope.
3. A judge can read it and see the API is **small, consistent, and fully specified** — not a pile of ad-hoc URLs.

**Three API families, one style:**

| Family | Base path | Provided by | You write |
|---|---|---|---|
| **Auth** | `/auth/v1/*` | Supabase Auth (GoTrue) | Nothing — call the SDK |
| **Data (CRUD)** | `/rest/v1/{table}` | PostgREST | Nothing — call the SDK |
| **RPC (reorder)** | `/rest/v1/rpc/{fn}` | PostgREST → your Postgres function | ~30 lines of SQL |

## 1. API Conventions

### 1.1 Base URLs

| Environment | Base URL |
|---|---|
| Local dev | `http://localhost:54321` (Supabase CLI) or your hosted project URL |
| Production | `https://<project-ref>.supabase.co` |

The frontend reads this from `VITE_SUPABASE_URL`. The `supabase-js` client builds every URL below — **you never construct these strings by hand.**

### 1.2 Required headers

Every data request carries these four headers. `supabase-js` adds them automatically:

```http
apikey: <VITE_SUPABASE_ANON_KEY>
Authorization: Bearer <user-jwt>
Content-Type: application/json
Prefer: return=representation
```

| Header | When | Why |
|---|---|---|
| `apikey` | **Always** | Identifies the Supabase project. The anon key is public by design. |
| `Authorization: Bearer <jwt>` | **All data requests** | Identifies the user. RLS uses `auth.uid()` from this JWT. |
| `Content-Type: application/json` | POST / PATCH / PUT | Tells PostgREST the body is JSON. |
| `Prefer: return=representation` | POST / PATCH / DELETE | Makes PostgREST return the affected rows instead of `204 No Content`. **Without this, a successful write returns an empty body** — a beginner trap. |

**Auth endpoints are the exception:** signup/login send only `apikey` + `Content-Type` (there's no JWT yet). Login *returns* the JWT.

### 1.3 Authentication requirement levels

Each endpoint below is tagged with one of:

| Tag | Meaning |
|---|---|
| **Public** | No JWT required (only `apikey`). Used for signup/login/refresh. |
| **Authenticated** | Valid JWT required. Missing/expired → `401`. |
| **Owner** | Valid JWT **and** the row belongs to the caller (enforced by RLS). Not owned → row invisible (`[]` on read, `0 rows` on write) → the API returns `404`-equivalent behavior. |

### 1.4 PostgREST query syntax (the only syntax you need)

PostgREST encodes filters and ordering in the query string. There are **no** `/goals/:id` paths — the ID is a filter. The patterns used in this app:

| Intent | Query string |
|---|---|
| Select all columns | `?select=*` |
| Filter by equality | `?id=eq.<uuid>` |
| Filter by multiple | `?goal_id=eq.<uuid>&completed_at=is.null` |
| Filter NULL | `?completed_at=is.null` |
| Sort ascending | `?order=order.asc` |
| Sort by two columns | `?order=goal_id.asc,order.asc` |
| Return a single object (not array) | `.single()` in `supabase-js` (adds `Accept: application/vnd.pgrst.object+json`) |

**Reserved-word note:** the column `"order"` is quoted in SQL, but in the URL it's just `order=order.asc`. PostgREST handles the quoting.

### 1.5 Standard response envelope

**Success (list):**
```json
[ { ...row }, { ...row } ]
```

**Success (single, via `.single()`):**
```json
{ ...row }
```

**Success (write, with `Prefer: return=representation`):**
```json
[ { ...the inserted/updated row } ]
```

**Error (uniform shape from PostgREST):**
```json
{
  "code": "23505",
  "details": "Key (user_id, name)=(a1b2…, DSA) already exists.",
  "hint": null,
  "message": "duplicate key value violates unique constraint \"goals_user_name_unique\""
}
```

**Auth errors** (GoTrue) use a slightly different shape:
```json
{ "error": "invalid_grant", "error_description": "Invalid login credentials" }
```

Document both in `repository.js` and normalize to `{ ok: false, status, code, message }` before the UI sees them.

### 1.6 Status code catalogue (what each means here)

| Status | When it happens | Typical Postgres/PostgREST code |
|---|---|---|
| **200 OK** | Successful GET / PATCH / RPC | — |
| **201 Created** | Successful POST with `return=representation` | — |
| **204 No Content** | Successful write **without** `Prefer: return=representation` | — |
| **400 Bad Request** | Malformed body, CHECK constraint violation, bad RPC args | `23514` (check), `22P02` (invalid uuid), `PGRST102` (bad JSON) |
| **401 Unauthorized** | Missing/invalid/expired JWT | `PGRST301`, `invalid_grant` |
| **403 Forbidden** | JWT valid but RLS `WITH CHECK` rejects the write | `42501` (insufficient privilege) |
| **404 Not Found** | Row doesn't exist **or isn't yours** (RLS returns 0 rows + `.single()`) | `PGRST116` |
| **409 Conflict** | Unique constraint violation (duplicate order, duplicate goal name) | `23505` |
| **422 Unprocessable** | Foreign key violation (goal_id doesn't exist) | `23503` |
| **500 Internal Server Error** | Postgres failure, function bug | — |

**A subtlety the team must internalize:** because RLS silently filters rows, **"not owned" looks identical to "doesn't exist"** — both yield an empty array (or `PGRST116` on `.single()`). This is correct security behavior: the API never confirms whether another user's row exists. Treat both as `404` in the UI.

## 2. Authentication Endpoints

Provided by Supabase Auth (GoTrue). The frontend calls these via `supabase.auth.*` — the HTTP details are documented so you can debug.

### 2.1 POST /auth/v1/signup — Create account

| Field | Value |
|---|---|
| **Method** | `POST` |
| **URL** | `/auth/v1/signup` |
| **Purpose** | Register a new user with email + password. Returns a JWT if email confirmation is disabled (recommended for the hackathon — see TRD AUTH-6). |
| **Auth** | **Public** (`apikey` only) |
| **Query params** | None |
| **Body** | `{ "email": string, "password": string }` |
| **Status codes** | `200` success · `400` invalid email/password · `422` email already registered · `500` |

**Example request**
```http
POST /auth/v1/signup
apikey: <ANON_KEY>
Content-Type: application/json

{ "email": "student@example.com", "password": "correct-horse-battery" }
```

**Example success response (200)**
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs…",
  "token_type": "bearer",
  "expires_in": 3600,
  "refresh_token": "v1.Mrq8…",
  "user": {
    "id": "a1b2c3d4-1111-2222-3333-444455556666",
    "email": "student@example.com",
    "created_at": "2026-11-13T09:00:00Z"
  }
}
```

**Errors**

| Status | Body | Cause | UI action |
|---|---|---|---|
| 400 | `{"error":"validation_failed","error_description":"Unable to validate email address: invalid format"}` | Bad email | Show inline error |
| 422 | `{"error":"user_already_exists","error_description":"User already registered"}` | Duplicate email | "Try logging in instead" |
| 500 | `{"error":"unexpected_failure"}` | Supabase down | Toast; retry |

> **supabase-js equivalent:** `await supabase.auth.signUp({ email, password })`

### 3.3 POST /rest/v1/goals — Create a goal

| Field | Value |
|---|---|

| **URL** | `/rest/v1/goals` |

```http

apikey: <ANON_KEY>
Authorization: Bearer <JWT>
Content-Type: application/json
Prefer: return=representation

{ "user_id": "a1b2c3d4-…", "name": "DSA", "daily_minutes": 60 }
```

**Example success response (201)**
```json
[
  {
    "id": "11111111-1111-1111-1111-111111111111",
    "user_id": "a1b2c3d4-…",
    "name": "DSA",
    "daily_minutes": 60,
    "created_at": "2026-11-01T09:05:00Z",
    "updated_at": "2026-11-01T09:05:00Z"
  }
]
```

**Errors**

| Status | Body (abridged) | Cause |
|---|---|---|
| 400 | `{"code":"23514","message":"new row for relation \"goals\" violates check constraint \"goals_name_not_blank\""}` | Empty/whitespace name |

| 403 | `{"code":"42501","message":"new row violates row-level security policy"}` | `user_id` ≠ caller |
| 409 | `{"code":"23505","message":"duplicate key value violates unique constraint \"goals_user_name_unique\""}` | Goal name already exists for this user |

> **Tip:** `user_id` is available from `supabase.auth.getUser()`. Fill it in the action, not the form.

|---|---|

| **URL** | `/rest/v1/goals?id=eq.{goalId}` |

**Example request**
```http
PATCH /rest/v1/goals?id=eq.11111111-1111-1111-1111-111111111111
apikey: <ANON_KEY>
Authorization: Bearer <JWT>
Content-Type: application/json
Prefer: return=representation

{ "daily_minutes": 75 }
```

**Example success response (200)**
```json
[
  {
    "id": "11111111-1111-1111-1111-111111111111",
    "user_id": "a1b2c3d4-…",
    "name": "DSA",
    "daily_minutes": 75,
    "created_at": "2026-11-01T09:05:00Z",
    "updated_at": "2026-11-13T10:22:00Z"
  }
]
```

**Errors**

| Status | Cause | UI action |
|---|---|---|
| 400 | CHECK violation | Inline validation |

> **Important:** because RLS filters first, a PATCH on a goal you don't own returns **`200` with `[]`** (0 rows affected). The repository must treat an empty array as `404` for `PATCH`/`DELETE`.

## 6. RPC Endpoints

### 6.1 POST /rest/v1/rpc/reorder_task — Move a task atomically

| Field | Value |
|---|---|
| **Method** | `POST` |
| **URL** | `/rest/v1/rpc/reorder_task` |
| **Purpose** | Move a task to a new queue position and renumber the affected range **inside one transaction**, with the `UNIQUE(goal_id, "order")` constraint deferred. This is the only way to reorder that can't corrupt the queue. |
| **Auth** | **Authenticated + Owner** — the function is `SECURITY INVOKER`, so it runs under the caller's RLS |
| **Body** | `{ "p_task_id": uuid, "p_new_order": integer }` (PostgREST maps body keys to function parameters by name) |
| **Status codes** | `200` (returns `null`) · `400` (bad args, out-of-range order) · `401` · `403` (task not owned) · `404` (task not found) · `500` |

**Example request**
```http
POST /rest/v1/rpc/reorder_task
apikey: <ANON_KEY>
Authorization: Bearer <JWT>
Content-Type: application/json

{ "p_task_id": "aaaa5555-…", "p_new_order": 2 }
```

**Example success response (200)**
```
null
```

(The function returns `void`. The client must **re-fetch** the goal's tasks — or re-derive from the in-memory list — to see the new order.)

**Before → after (visualized)**

```
Before:  [1: Arrays] [2: Two ptrs] [3: Sliding] [4: Binary] [5: Recursion]
Call:    reorder_task(task=Recursion(id aaaa5555), new_order=2)
After:   [1: Arrays] [2: Recursion] [3: Two ptrs] [4: Sliding] [5: Binary]
```

**Errors**

| Status | Body (abridged) | Cause |
|---|---|---|
| 400 | `{"code":"P0001","message":"Task aaaa5555-… not found"}` | Bad `p_task_id` |
| 400 | `{"code":"P0001","message":"p_new_order must be >= 1"}` | Invalid target position |
| 400 | `{"code":"P0001","message":"p_new_order 9 exceeds max order 5"}` | Target beyond the queue |
| 403 | `{"code":"42501","message":"permission denied for table tasks"}` | Task belongs to another user (RLS blocks the internal `UPDATE`) |
| 500 | `{"code":"23505","message":"duplicate key value violates unique constraint \"tasks_goal_order_unique\""}` | Should be impossible — the constraint is deferred. If you see it, the `SET CONSTRAINTS … DEFERRED` line is missing. |

> **supabase-js:** `await supabase.rpc('reorder_task', { p_task_id: id, p_new_order: n })`
>
> **Why an RPC and not two PATCHes?** Reordering moves *multiple* rows (all rows between the old and new position). Doing that as N independent PATCHes can fail halfway and leave the queue duplicated or gapped. The RPC is atomic — it either fully succeeds or fully rolls back. This is the **only** place we need server-side logic beyond CRUD, and it's ~30 lines of SQL.

## 7. Composite Read Pattern (not an endpoint)

The app's boot sequence needs goals + tasks + rest_days. There is **no `GET /api/snapshot` endpoint** — and deliberately so. The repository issues three parallel requests:

```js
// lib/repository.js — fetchAll()
const [goals, tasks, restDays] = await Promise.all([
  supabase.from('goals').select('*').order('created_at.asc'),
  supabase.from('tasks').select('*').order('goal_id.asc,order.asc'),
  supabase.from('rest_days').select('*').order('goal_id.asc,date.asc'),
]);
```

| Concern | How it's handled |
|---|---|
| Parallelism | `Promise.all` — total latency ≈ slowest query (~100 ms) |
| Consistency | Not transactional, but single-user data changes only from this client; a rare mid-flight edit self-heals on the next `reload()` |
| Payload size | ~5,000 tasks ≈ 1–2 MB JSON — fine at this scale |

**Why not add a view or RPC that joins all three?** It would save two round-trips (~50 ms) and add a server-side artifact to maintain. At this scale, three parallel GETs are simpler and faster to build. If the payload ever exceeds ~5 MB, revisit.

## 8. Error Catalogue (what to handle in `repository.js`)

| HTTP | Postgres / PostgREST code | Meaning | What the UI should do |
|---|---|---|---|
| 400 | `23514` | CHECK constraint failed | Inline field error |
| 400 | `22P02` | Invalid input syntax (bad uuid/date/timestamp) | Client bug — log it |
| 400 | `PGRST102` | Malformed JSON body | Client bug — log it |
| 400 | `P0001` | RPC `RAISE EXCEPTION` (bad reorder args) | Toast the message |
| 401 | `PGRST301` / `invalid_grant` | JWT missing/expired | Attempt refresh → else redirect `/login` |
| 403 | `42501` | RLS `WITH CHECK` rejected the write | "You can't modify this" — should never happen in normal use |
| 404 | `PGRST116` | `.single()` found 0 rows (missing **or** not owned) | "Not found" — same UI for both |
| 404 | *(empty `[]`)* | Row not owned/deleted on PATCH/DELETE | Treat as `404` in the repository |
| 409 | `23505` | Unique violation (goal name, task order, rest day) | Context-specific message |
| 422 | `23503` | Foreign key violation (bad `goal_id`) | "Goal was deleted — refreshing" → `reload()` |
| 500 | — | Server/database failure | Toast + retry button |

**Normalization contract** — every repository function returns one of:

```js
{ ok: true,  data }                                  // success
{ ok: false, status, code, message, retryable }      // failure
```

`retryable = true` for `401` (after refresh) and `5xx`; `false` for `4xx` validation errors. `AppContext` uses `retryable` to decide toast vs. rollback-and-redirect.

## 10. Endpoints We Deliberately Do NOT Have

This list matters as much as §9. It's the answer to *"why doesn't your API have X?"*

| Hypothetical endpoint | Why it doesn't exist |
|---|---|
| `GET /api/projection` | Projection is a **pure function of `tasks` + `today`**. The client already has `tasks`. A server endpoint would compute the same number and add a round-trip. |
| `GET /api/streaks` | Same — computed from `completed_at` + `rest_days`, both already client-side. |
| `GET /api/heatmap` | Same — a `Set` of dates from `completed_at`. |
| `GET /api/dashboard/{goalId}` | Would bundle data the client already fetched via `fetchAll()`. |
| `GET /api/tasks/search?q=…` | Search is a substring filter over the in-memory queue. Zero latency, no endpoint. |
| `GET /api/tasks?offset=…&limit=…` (pagination) | Single-user data (< 5,000 tasks). Fetching everything is simpler and faster. |
| `POST /api/tasks/{id}/complete` | A `PATCH` on `completed_at` is the same thing with fewer invented verbs. |
| `PUT /rest/v1/tasks/{id}` | `PATCH` (partial update) is what the UI actually does. `PUT` (full replace) would force the client to resend every column — a bug magnet. |
| `POST /api/goals/{id}/roadmap` | Bulk insert **is** `POST /rest/v1/tasks` with an array body (§4.4). No new endpoint needed. |
| `GET /api/notifications` | Shift notices are derived from the same projection data. In-app only, nothing to persist or fetch. |
| `POST /api/export` | A client-side `SELECT *` + `Blob` download (PRD nice-to-have). No server needed. |
| `POST /api/ai/roadmap` | **No AI features in this product** (PRD §15). |
| `POST /api/webhooks/stripe` | No payments. |
| `GET /api/admin/*` | Single-user app. No admin role. |
| Any `websocket` / realtime channel | Single user, single device at a time. `reload()` after mutation is sufficient. Realtime is a post-MVP upgrade. |

**The principle:** every endpoint is an attack surface, a document to maintain, and a thing to break during the demo. We add one only when the client **cannot** derive the answer from data it already has, or when the operation **must** be atomic (reorder). Nothing else qualifies.

## Appendix A — 60-second judge explanation

> "The API is 19 operations across 6 URL patterns — all served by Supabase's auto-generated PostgREST layer, plus one Postgres function for atomic reordering. We wrote zero HTTP handlers. Access control is enforced by Row Level Security, so a `PATCH` on someone else's task returns an empty array rather than leaking whether it exists. The reason the API is so small is that we don't expose derived data: projections, streaks, and heatmaps are pure functions in the browser over data the client already has. The one place we *did* need server logic is reordering, because moving a task shifts multiple rows and must be atomic — that's the `reorder_task` RPC, and it's about thirty lines of SQL."
